# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

MeStar (mestar.pro) is a personalized digital storybook e-commerce site: a customer uploads a
child's photo, picks a theme, and the site generates an illustrated, personalized storybook (plus
optional audiobook/coloring-pages/PDF add-ons). It's a **Lovable**-managed project — see the
"Lovable specifics" section below.

Stack: Vite + React 18 + TypeScript + shadcn/ui (Radix) + Tailwind on the frontend, Zustand for
client state, Shopify (Storefront API) as the cart/checkout backend, Stripe for embedded payment,
and Supabase (Postgres + Deno Edge Functions) as the app backend and generation pipeline.

## Commands

```sh
npm run dev          # Vite dev server on :8080
npm run build         # vite build, then scripts/prerender.mjs (SSG prerender for SEO)
npm run build:dev     # dev-mode build (skips prod minification), still prerenders
npm run lint           # eslint .
npm run test            # vitest run (single pass)
npm run test:watch     # vitest watch mode
npx vitest run src/path/to/file.test.ts   # run a single test file
npx playwright test                        # e2e tests (config: playwright.config.ts, uses lovable-agent-playwright-config)
```

There is no separate typecheck script; `vite build` / your editor's TS server is the check.

## Architecture

### Frontend structure
- `src/pages/*` — route-level components, wired up in `src/App.tsx` (plain `react-router-dom`
  `<Routes>`, no nested/lazy routing).
- `src/components/ui/*` — shadcn/ui primitives (generated via `components.json`, alias `@/components/ui`).
  Don't hand-edit generated primitives beyond what shadcn's own codegen produces; add app-specific
  components in `src/components/` instead.
- `src/stores/cartStore.ts` — single Zustand store (persisted to `localStorage` under the key
  `shopify-cart`) holding cart items, Shopify `cartId`/`checkoutUrl`, and per-item
  `Personalization` (child name/age/theme/photo/add-ons). `useCartSync` (in `src/hooks`) keeps it
  reconciled with Shopify on mount.
- `src/lib/shopify.ts` — all Shopify Storefront API calls (create/update/remove cart lines, fetch
  cart, recreate cart). The cart store is a thin state wrapper around this.
- `src/lib/stripe.ts` — loads Stripe.js using `VITE_PAYMENTS_CLIENT_TOKEN`; the `pk_test_`/`pk_live_`
  prefix of that token determines sandbox vs. live (`getStripeEnvironment()`), which is then passed
  through to the `create-checkout` edge function.
- `src/lib/products.ts` — local product/pricing config (base story + supporting-character and
  audiobook add-ons), including their Shopify variant GIDs. This is the source of truth for
  prices/variant IDs on the client; keep it in sync with the Shopify catalog.
- `src/integrations/supabase/{client.ts,types.ts}` — **auto-generated by Supabase tooling; do not
  hand-edit.** Regenerate `types.ts` from the Supabase schema instead of patching it.
- `src/entry-server.tsx` + `scripts/prerender.mjs` — post-build static prerendering. After
  `vite build`, the script SSR-renders a fixed list of public marketing/catalog routes (home,
  /about, /faq, /products/*, etc. — auth/checkout/admin routes are intentionally excluded) via
  `react-dom/server` and writes real HTML + `<head>` (react-helmet-async output) into `dist/` for
  crawlers; client hydration in `main.tsx` takes over from there. Update the `ROUTES` array in that
  script when adding new public pages that should be crawlable.
- `src/lib/mcp/` — a public MCP tool server (`@lovable.dev/mcp-js`, wired in via the `mcpPlugin()`
  Vite plugin) exposing read-only catalog tools (`list_products`, `get_product`, `list_story_themes`)
  for AI agents. It intentionally exposes no customer/order data.

### Order & generation pipeline (Supabase edge functions)

Orders live in the `storybook_orders` table and move through a status state machine:

```
pending_payment → queued → generating_story → generating_images → assembling_pdf → complete
                                                                                   ↘ failed
```

Key functions in `supabase/functions/`:
- `create-pending-order` — creates the order row before checkout.
- `create-checkout` — creates the Stripe Checkout session (uses `_shared/stripe.ts`, keyed by
  `environment: "sandbox" | "live"`); maps Stripe price IDs to `selected_addons` on the order.
- `stripe-webhook` — verifies the Stripe signature, then fires the generation pipeline.
- `confirm-checkout-payment` — return-URL fallback that also fires the pipeline (belt-and-suspenders
  in case the webhook is delayed/missed).
- `generate-story` / `create-storybook` / `generate-audiobook` — the actual content-generation
  pipeline steps.
- `get-order-status`, `get-audiobook` — client polling/reads.
- `order-health-check` — cron-style monitor; `mode=failures` alerts on `status='failed'` or orders
  stuck >30min in a non-terminal status, `mode=daily` sends a daily summary.
- `send-order-notification`, `send-transactional-email`, `process-email-queue`,
  `handle-email-unsubscribe`, `handle-email-suppression`, `subscribe-email` — transactional email.
- `shopify-order-webhook` — inbound Shopify order events.
- `_shared/stripe.ts` — shared Stripe client construction (sandbox/live); `_shared/transactional-email-templates/` — shared email templates.

**Critical convention:** generation is slow (60s+) and Stripe's webhook timeout is ~10s. Both
`stripe-webhook` and `confirm-checkout-payment` fire the pipeline via
`EdgeRuntime.waitUntil(fireGeneration(orderId).catch(...))` rather than `await`-ing it directly, so
the HTTP response returns immediately while generation continues in the background. Any new
webhook/return-URL handler that kicks off generation must follow the same pattern — an `await` here
reintroduces the 504-timeout bug (see `.lovable/plan.md` for the incident writeup).

Edge functions requiring no JWT (public-facing) are listed in `supabase/config.toml` under
`[functions.<name>] verify_jwt = false`; anything not listed there requires a Supabase JWT.

### Environment variables
Client (`VITE_`-prefixed, read via `import.meta.env`): `VITE_SUPABASE_URL`,
`VITE_SUPABASE_PUBLISHABLE_KEY`, `VITE_SUPABASE_PROJECT_ID`, `VITE_PAYMENTS_CLIENT_TOKEN` (Stripe
publishable key), `VITE_STRIPE_PRICE_*` (Stripe price IDs per product/add-on). Edge functions read
their own secrets from `Deno.env` (Supabase service role key, Stripe secret key, etc.) — never
expose those to the client.

### Testing
- Unit/component tests: Vitest + `@testing-library/react`, jsdom environment, setup file at
  `src/test/setup.ts`. Test files match `src/**/*.{test,spec}.{ts,tsx}`.
- E2E: Playwright, configured via the shared `lovable-agent-playwright-config` preset in
  `playwright.config.ts`.

## Lovable specifics
This project is developed/deployed through [Lovable](https://lovable.dev):
- `vite.config.ts` conditionally loads `lovable-tagger`'s `componentTagger()` in dev mode only —
  don't remove it, it's what lets the Lovable editor map DOM back to source.
- `.lovable/plan.md` holds the most recent Lovable agent plan/incident notes — useful historical
  context but not a standing spec.
- `bun.lock` and `package-lock.json` are both present; check which one CI/Lovable actually uses
  before assuming a package manager.
